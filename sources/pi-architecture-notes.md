## 2. packages/ai (`pi-ai`) — unified LLM API

**Layering.** The root export (`src/index.ts:4-8`) is deliberately side-effect-free: "Core only… no generated catalogs, no provider factories… Provider factories live under `pi-ai/providers/*`, API implementations under `pi-ai/api/*`, the old global API under `pi-ai/compat`". `src/compat.ts:1-11` is a "temporary compatibility entrypoint" preserving the old global `stream()`/`complete()` + env-key injection, kept until the coding-agent's ModelManager migration finishes.

**Core data model** (`src/types.ts`):
- `Api` — 9 known API protocol implementations (`types.ts:15-24`): `openai-completions`, `openai-responses`, `azure-openai-responses`, `openai-codex-responses`, `anthropic-messages`, `bedrock-converse-stream`, `google-generative-ai`, `google-vertex`, `mistral-conversations` (plus open string). `KnownProvider` lists ~36 providers (`types.ts:32-67`) incl. anthropic, openai, openai-codex, github-copilot, google, bedrock, groq, cerebras, openrouter, zai, moonshotai, xiaomi token plans, etc.
- `Model<TApi>` (`types.ts:697-722`): `id, name, api, provider, baseUrl, reasoning, thinkingLevelMap, input: ("text"|"image")[], cost: ModelCost (with tiered pricing), contextWindow, maxTokens, compat` (compat type varies by API via conditional type).
- `Context` = `{ systemPrompt?, messages: Message[], tools?: Tool[] }` (`types.ts:445-449`). `Tool` = `{ name, description, parameters: TSchema }` — **TypeBox** JSON-schema, not zod (`types.ts:439-443`).
- `Message` union: `UserMessage | AssistantMessage | ToolResultMessage` (`types.ts:414`). `AssistantMessage.content` is `(TextContent | ThinkingContent | ToolCall)[]`, plus `api/provider/model/usage/stopReason/errorMessage/timestamp` (`types.ts:383-396`). `StopReason = "stop" | "length" | "toolUse" | "error" | "aborted"` (`types.ts:375`). `ToolResultMessage` carries `content: (TextContent|ImageContent)[]`, `details`, `isError`, and `addedToolNames?: string[]` — names of tools that became available after this result (deferred tool loading, `types.ts:398-412`).
- `Usage` (`types.ts:352-373`): `input/output/cacheRead/cacheWrite/cacheWrite1h?/reasoning?/totalTokens` + nested `cost` breakdown. `calculateCost()` (`models.ts:386-406`) applies request-wide pricing tiers and Anthropic's "2x base input for 1h cache writes" rule.

**Streaming.** `AssistantMessageEvent` (`types.ts:459-471`) is the wire protocol: `start`, then `text_start/text_delta/text_end`, `thinking_start/…`, `toolcall_start/toolcall_delta/toolcall_end`, terminated by `done {reason}` or `error {reason: "aborted"|"error"}`. Every partial event carries the accumulating `partial: AssistantMessage`. `EventStream<T,R>` (`utils/event-stream.ts:4-67`) is a push-based async-iterable queue with a `result(): Promise<R>` resolved by the terminal event; `AssistantMessageEventStream` specializes it. Hard contract (`types.ts:296-308`): stream functions **never throw** — all failures are encoded in the stream as an `error` event whose payload is an `AssistantMessage` with `stopReason: "error"|"aborted"` and `errorMessage`.

**Providers vs APIs.** Each API module under `src/api/` exports exactly `stream` and `streamSimple` (`ProviderStreams`, `types.ts:222-225`); `.lazy.ts` twins defer importing the heavy SDKs (`@anthropic-ai/sdk`, `openai`, `@google/genai`, `@aws-sdk/client-bedrock-runtime`, `@mistralai/mistralai`) until first use. A **`Provider`** (`models.ts:33-73`) owns id/baseUrl/auth/model list/stream dispatch; `createProvider()` (`models.ts:324-370`) assembles one from parts (used by both built-in factories like `anthropicProvider()` in `providers/anthropic.ts:7-21` and user `models.json` custom providers). **`Models`** (`models.ts:80-129`, built via `createModels()`) is the runtime collection: `getProviders/getModels/getModel/refresh/getAuth`, plus `stream/complete/streamSimple/completeSimple` — the entry API. `Models.stream()` resolves auth (`applyAuth`, `models.ts:231-257`: OAuth token refresh, env-key lookup, baseUrl/header overrides) then delegates to the owning provider. `complete()` is just `this.stream(...).result()` (`models.ts:271-277`). `streamSimple` accepts `SimpleStreamOptions` with a unified `reasoning?: ThinkingLevel` ("minimal"→"max") and `thinkingBudgets`, which each API maps to its provider-native thinking parameter.

**Model registry.** `models.generated.ts` + per-provider `*.models.ts` files are generated at build by `scripts/generate-models.ts`, which fetches `https://models.dev/api.json`, the OpenRouter catalog, and Vercel AI Gateway, then applies hand-maintained overrides — **1,057 models** currently. AGENTS.md:24 forbids editing the generated files directly. Dynamic providers (OpenRouter, gateways, Copilot) also support runtime `refreshModels()`.

**Compat shims.** For OpenAI-compatible endpoints, `OpenAICompletionsCompat` (`types.ts:477-524`) has ~20 quirk flags auto-detected from `baseUrl` but overridable per model: `maxTokensField`, `requiresToolResultName`, `requiresThinkingAsText`, and a `thinkingFormat` enum with **10 dialects** (`"openai" | "openrouter" | "deepseek" | "together" | "zai" | "qwen" | "chat-template" | "qwen-chat-template" | "string-thinking" | "ant-ling"`), plus OpenRouter/Vercel routing preferences and `cacheControlFormat: "anthropic"`. `AnthropicMessagesCompat` (`types.ts:539-590`) covers eager tool-input streaming, 1h cache TTL, adaptive thinking (`forceAdaptiveThinking` — set on `claude-fable-5` in the generated catalog), and `supportsToolReferences` for deferred tools.

**Caching.** `CacheRetention = "none" | "short" | "long"` (`types.ts:96`, default "short", env `PI_CACHE_RETENTION`). The Anthropic adapter places `cache_control: {type:"ephemeral", ttl?:"1h"}` markers on the system prompt, tool definitions (if `supportsCacheControlOnTools`), and the last user message (`anthropic-messages.ts:924-1237`). OpenAI paths use `prompt_cache_retention: "24h"` and a `session_id` affinity header from `StreamOptions.sessionId` (`openai-prompt-cache.ts`, `OpenAIResponsesCompat.sendSessionIdHeader`). Anthropic-compatible hosts like Fireworks get `x-session-affinity` headers.

**Tool schema passing.** TypeBox schemas are passed essentially verbatim as JSON Schema — e.g. Anthropic `input_schema: { type: "object", properties, required }` (`anthropic-messages.ts:1268-1276`). `validateToolArguments` (`utils/validation.ts`) validates LLM-produced args against the schema before execution; `parseStreamingJson`/`parseJsonWithRepair` (`utils/json-parse.ts`, uses `partial-json`) salvage streamed tool-call argument JSON.

**Notable extras**:
- **Stealth mode**: for Anthropic OAuth traffic the adapter "Mimic[s] Claude Code's tool naming exactly" — a `claudeCodeTools` list (Read/Write/Edit/Bash/Grep/Glob/AskUserQuestion/EnterPlanMode/…) and `claudeCodeVersion = "2.1.75"` sourced from the author's `cchistory` project (`anthropic-messages.ts:76-90`).
- **Overflow detection**: `utils/overflow.ts` has ~24 regex patterns for context-overflow errors across providers, with comments documenting each provider's exact error text, plus heuristics for providers that don't error (z.ai accepts overflow silently → detected via `usage.input > contextWindow`; Xiaomi MiMo truncates and returns `length` with zero output).
- **Retry classification**: `utils/retry.ts` `isRetryableAssistantError()` with curated retryable patterns (429/5xx/overloaded/socket/`stream ended before message_stop`…) and non-retryable quota/billing patterns, each annotated with issue numbers.
- **Deferred tools**: `splitDeferredTools()` (`utils/deferred-tools.ts:8-40`) splits `Context.tools` into an immediate prefix and transcript-loaded tools introduced via `ToolResultMessage.addedToolNames`; Anthropic loads them via `tool_reference` blocks, OpenAI Responses via client-executed tool search (`supportsToolSearch`).
- **Message transforms**: `transformMessages()` (`api/transform-messages.ts:64`) normalizes tool-call IDs cross-provider (OpenAI Responses IDs can be 450+ chars; Anthropic requires `^[a-zA-Z0-9_-]+$` ≤64) and downgrades images to text placeholders for non-vision models — this is what makes a session **portable across providers mid-conversation**.
- OAuth implementations in `utils/oauth/`: `anthropic` (Claude Pro/Max), `openai-codex` (ChatGPT plan), `github-copilot` (device code); PKCE + device-code helpers; a small `pi-ai` bin (`src/cli.ts`) for logging in and dumping an `auth.json`.
- Transports: `Transport = "sse" | "websocket" | "websocket-cached" | "auto"` (`types.ts:98`; the Codex adapter has a WebSocket transport with debug stats). Proxy support via `http(s)-proxy-agent`, OTel API dep for tracing hooks (`onPayload`/`onResponse` callbacks in `StreamOptions`, `types.ts:130-139`).
- Image generation is a parallel mini-stack (`ImagesModel`, `generateImages`, `openrouter-images` API).

## 3. packages/agent (`pi-agent-core`) — the runtime

Three layers: a **pure functional loop** (`agent-loop.ts`), a **stateful `Agent` class** (`agent.ts`), and a newer **portable `AgentHarness`** (`harness/`).

**The loop** (`src/agent-loop.ts`). Entry points `agentLoop(prompts, context, config, signal?, streamFn?)` and `agentLoopContinue(...)` (lines 31-93) return `EventStream<AgentEvent, AgentMessage[]>`. `runLoop()` (lines 155-275) step by step:
1. Poll `config.getSteeringMessages?.()` once up front ("user may have typed while waiting", line 166-167).
2. **Outer loop** (`while(true)`, line 170) — continues when follow-up messages arrive after the agent would stop. **Inner loop** (line 174) runs `while (hasMoreToolCalls || pendingMessages.length > 0)`.
3. Emit `turn_start`; inject pending steering messages into context (emitting `message_start`/`message_end` for each).
4. `streamAssistantResponse()` (lines 281-374): applies `config.transformContext` (AgentMessage[]→AgentMessage[], for pruning/injection), then `config.convertToLlm` (AgentMessage[]→LLM `Message[]` — filters app-custom messages), builds the `Context`, resolves the API key fresh via `config.getApiKey` ("important for expiring tokens", line 306), calls `streamFn` (default `streamSimple`). While streaming, the partial `AssistantMessage` is pushed/replaced in `context.messages`, and each `AssistantMessageEvent` is re-emitted as `{type:"message_update", assistantMessageEvent, message}`.
5. If `stopReason` is `error`/`aborted`: emit `turn_end` + `agent_end`, return.
6. **Truncation guard**: if `stopReason === "length"`, *all* tool calls are failed without execution — "arguments may be truncated… none of them are safe to execute" (`failToolCallsFromTruncatedMessage`, lines 383-408).
7. Otherwise `executeToolCalls()` (lines 413-428): mode is `config.toolExecution` (**default "parallel"**) but any tool with `executionMode: "sequential"` forces the whole batch sequential. Sequential path: prepare→execute→finalize one by one. Parallel path (lines 491-556): each call is **prepared sequentially** (`prepareToolCall`: look up tool, `prepareArguments` shim, `validateToolArguments`, `beforeToolCall` hook which can `{block, reason}`), then allowed calls execute concurrently; `tool_execution_end` is emitted in completion order, but `toolResult` messages are appended **in assistant source order** (comment at `types.ts:36-40`).
8. Tool execution (`executePreparedToolCall`, lines 668-709): calls `tool.execute(toolCallId, args, signal, onUpdate)`; `onUpdate` partials become `tool_execution_update` events; throws become error tool results. `afterToolCall` hook can override `content/details/isError/terminate` (lines 711-755).
9. Early termination: if **every** finalized result in the batch sets `terminate: true`, the loop stops after the batch (`shouldTerminateToolBatch`, line 584).
10. Emit `turn_end {message, toolResults}`; run `config.prepareNextTurn` (can swap `context`/`model`/`thinkingLevel` for the next request — used for compaction and mid-run model switching); check `config.shouldStopAfterTurn`; poll steering again.
11. When no tool calls and no steering remain, poll `config.getFollowUpMessages?.()`; if any, loop again; else emit `agent_end {messages}`.

**Event vocabulary** (`types.ts:415-430`): `agent_start`, `agent_end`, `turn_start`, `turn_end`, `message_start`, `message_update`, `message_end`, `tool_execution_start`, `tool_execution_update`, `tool_execution_end`.

**Tool interface** `AgentTool<TParameters extends TSchema, TDetails>` (`types.ts:373-396`): `name/description/parameters` (TypeBox) + `label`, `prepareArguments?` (compat shim run before validation), `execute(toolCallId, params: Static<TParameters>, signal?, onUpdate?)` returning `AgentToolResult<T> = { content: (TextContent|ImageContent)[], details: T, addedToolNames?, terminate? }`, and `executionMode?`.

**The `Agent` class** (`agent.ts:171-575`): owns `AgentState` (`systemPrompt`, `model`, `thinkingLevel`, `tools`, `messages`, `isStreaming`, `streamingMessage`, `pendingToolCalls`, `errorMessage`; array assignments copy — `types.ts:322-347`). Public API: `prompt(text|message|messages)`, `continue()`, `steer(msg)`, `followUp(msg)` (queues backed by `PendingMessageQueue` with `QueueMode = "all" | "one-at-a-time"`, default **one-at-a-time**, `agent.ts:222-223`), `clear*Queue()`, `abort()`, `waitForIdle()`, `reset()`, `subscribe(listener)` — listener promises are **awaited in subscription order and are part of run settlement** (`agent.ts:241-244`), which is how session persistence stays ordered. `prompt()` while running throws ("Use steer() or followUp()", `agent.ts:339`). `continue()` from a trailing assistant message drains queued steering/follow-up instead (`agent.ts:358-372`). Run failures synthesize an assistant error message and emit a full `message_start/message_end/turn_end/agent_end` sequence (`handleRunFailure`, `agent.ts:494-510`). Custom app message types plug in via **declaration merging** on `CustomAgentMessages` (`types.ts:305-314`).

**`proxy.ts`** defines a bandwidth-reduced `ProxyAssistantMessageEvent` protocol (partials stripped, lines 36-50) plus a client stream fn for apps that route LLM calls through a server that holds credentials.

**`harness/`** is a newer, environment-agnostic re-implementation of the app layer: `AgentHarness` class (`harness/agent-harness.ts:157`), portable `ExecutionEnv`/`FileSystem` abstraction (`harness/env/nodejs.ts`), session storage (`session/jsonl-storage.ts`, `memory-storage.ts`, repos), compaction, skills, prompt templates, system prompt — all exported from the package root (`index.ts:5-42`). It shares the JSONL format with coding-agent but adds durable leaf persistence (`leaf` entries) and an `active_tools_change` entry, and is stricter (only session `version: 3`). The coding-agent still uses its own older `AgentSession`/`SessionManager`; the harness is the reusable core for other hosts (e.g. the separate `pi-chat` repo).

## 4. packages/coding-agent (`pi-coding-agent`) — the CLI product

**Entry & modes.** `bin.pi → dist/cli.js`; `src/main.ts` parses args (`cli/args.ts`) and builds a session via the SDK (`core/sdk.ts createAgentSession`). Four modes (`resolveAppMode`, `main.ts:100-111`): **interactive** TUI (default on TTY), **print** (`-p`, also auto-selected when stdin/stdout is not a TTY), **json** (`--mode json`, print mode emitting the full event stream as JSON), **rpc** (`--mode rpc`, newline-delimited JSON over stdin/stdout; also `./rpc-entry` export). The RPC protocol (`modes/rpc/rpc-types.ts:20-72`) exposes ~30 commands: `prompt/steer/follow_up/abort`, `new_session/switch_session/fork/clone`, `get_state/get_messages/get_entries/get_tree`, `set_model/cycle_model/get_available_models`, `set_thinking_level`, `set_steering_mode/set_follow_up_mode`, `compact/set_auto_compaction`, `set_auto_retry/abort_retry`, `bash/abort_bash`, `get_session_stats/export_html/set_session_name/get_commands`. CLI flags include `--continue/--resume/--fork/--session-dir/--no-session`, `--models` (scoped cycling), `--tools/--no-builtin-tools/--exclude-tools`, `--extension/--no-extensions`, `--skill/--no-skills`, `--prompt-template`, `--system-prompt/--append-system-prompt`, `--thinking`, `--approve/--no-approve`, `--offline`, `--export`.

**Central runtime: `AgentSession`** (`core/agent-session.ts`, 3,246 LOC) wraps `Agent` and layers: session persistence, settings, extensions, auto-compaction, auto-retry, user-bash, model switching. It extends the event union with `agent_settled`, `queue_update`, `compaction_start/end` (reason `"manual"|"threshold"|"overflow"`), `entry_appended`, `session_info_changed`, `thinking_level_changed`, `auto_retry_start/end` (lines 127-153). Event flow (`_handleAgentEvent`, lines 548-619): extension handlers run first, then UI listeners, then persistence (`sessionManager.appendMessage`) on `message_end`.

- **Auto-retry**: defaults `enabled: true, maxRetries: 3, baseDelayMs: 2000` exponential (2s/4s/8s) (`settings-manager.ts:813-817`). `_prepareRetry` (lines 2587-2637) pops the error assistant message from agent state (kept in the session file for history), sleeps abortably, then `agent.continue()`. Context overflow is explicitly *not* retryable (`_isRetryableError`, line 2577-2581) — it routes to compaction.
- **Overflow recovery**: on a provider overflow error, one **compact-and-retry** attempt (`_overflowRecoveryAttempted` flag; error message removed from context, compaction run with reason `"overflow"`, then continue; a second overflow gives up with a user-facing message) (`_checkCompaction`, lines 1926-1958).
- **Auto-compaction trigger** (lines 1960-1988): prefers real usage from the last assistant message (`calculateContextTokens`), falls back to a `chars/4` estimate anchored at the last valid usage; `shouldCompact = contextTokens > contextWindow - reserveTokens`.

**Built-in tools** (`core/tools/`): exactly seven — `read`, `bash`, `edit`, `write`, `grep`, `find`, `ls` — all TypeBox-schema'd `ToolDefinition`s wrapped into `AgentTool`s (`tool-definition-wrapper.ts:5-19`). **Default active set is only `[read, bash, edit, write]`** (`agent-session.ts:175`, `system-prompt.ts:90`, README: "By default, pi gives the model four tools"); grep/find/ls exist as opt-ins (`createReadOnlyTools`, `tools/index.ts:147-154`). Key implementation details:
- Shared truncation constants: `DEFAULT_MAX_LINES = 2000`, `DEFAULT_MAX_BYTES = 50*1024`, `GREP_MAX_LINE_LENGTH = 500` (`tools/truncate.ts:11-13`). `truncateHead` for read/grep/find/ls, `truncateTail` for bash.
- `read`: 1-indexed `offset`/`limit`; truncation footer teaches continuation (`[Showing lines A-B of TOTAL. Use offset=N to continue.]`, `read.ts:301-303`); native **image support** (jpg/png/gif/webp/bmp) with auto-resize to 2000×2000 via photon-wasm (`read.ts:59,243-250`).
- `bash`: `spawn` with the user's shell (`/bin/bash` fallback chain), `detached` on Unix so aborts can `process.kill(-pid, "SIGKILL")` the whole group (`shell.ts:200-225`); optional `timeout` in seconds, no default; output streamed through an `OutputAccumulator` that spills full output to a temp file (`pi-bash-*.log`) and tail-truncates to 2000 lines/50KB, with the footer pointing at the full file (`bash.ts:379-390`); non-zero exit throws `Command exited with code N`. No background mode by design (philosophy: "use tmux").
- `edit`: parameter shape is `{ path, edits: [{oldText, newText}] }` (multi-edit, no `replace_all`). Matching pipeline (`edit-diff.ts`): BOM strip → CRLF/CR→LF normalize → **exact `indexOf` first**, then a **fuzzy pass** normalizing NFKC, trailing whitespace per line, smart quotes, Unicode dashes, and exotic spaces (`edit-diff.ts:33-54,206-244`); uniqueness enforced ("Found N occurrences… must be unique"), overlap detection, "No changes made" detection; fuzzy replacements are overlaid so untouched lines keep their original bytes; diffs produced with `diff` (`Diff.diffLines` display diff + unified patch). A `prepareArguments` shim tolerates model quirks (stringified `edits`, legacy top-level `oldText/newText` — comment cites Opus 4.6/GLM-5.1, `edit.ts:94-118`).
- `edit`/`write` serialize concurrent mutations per real path via `withFileMutationQueue` (realpath-keyed promise chains, `file-mutation-queue.ts:32-61`).
- `grep` shells out to **ripgrep** `--json` (auto-downloaded via `ensureTool("rg")`), default limit 100 matches, kills rg at limit; `find` uses **fd** (`--glob --hidden`, default limit 1000); `ls` is plain readdir (limit 500).

**System prompt — deliberately tiny.** `buildSystemPrompt()` (`core/system-prompt.ts:28-173`) produces ~25 lines: role sentence, an "Available tools" list built from per-tool one-line `promptSnippet`s, a few guidelines (extensions can append via `promptGuidelines`), then **pointers to pi's own shipped docs** ("read only when the user asks about pi itself…" with absolute paths to README/docs/examples — the "agent can explain itself" mechanism), optional `appendSystemPrompt`, project context files wrapped in `<project_context>/<project_instructions path=…>`, the `<available_skills>` block, and finally date + cwd. Context files: `AGENTS.md`/`CLAUDE.md` are loaded regardless of project trust (security.md:29).

**Sessions** (from `session-manager.ts` + `docs/session-format.md`): JSONL files at `~/.pi/agent/sessions/--<cwd-encoded>--/<timestamp>_<uuidv7>.jsonl`. Line 1 is a `SessionHeader {type:"session", version:3, id, timestamp, cwd, parentSession?}`; all other entries form a **tree** via `{id (8-char), parentId}`: entry types `message`, `thinking_level_change`, `model_change`, `compaction {summary, firstKeptEntryId, tokensBefore, details}`, `branch_summary {fromId, summary}`, `custom` (extension state, not in LLM context), `custom_message` (in context), `label`, `session_info` (+ harness-only `leaf`, `active_tools_change`). **Branching is in-file**: `/tree` navigation and message-editing just move the leaf pointer (`branch(id)`, `session-manager.ts:1289-1294`), optionally appending a `branch_summary` generated from the abandoned branch; `/fork` and `/clone` extract root→leaf into a new file with `parentSession` back-reference. File creation is deferred until the first assistant message to avoid empty sessions (`_persist`, lines 946-973). Versioned migrations v1→v2→v3 run on load. Session stats/`/session`, HTML export (`core/export-html/`), `/share` (secret gist), and cross-project `--fork` round out portability.

**Compaction** (`core/compaction/compaction.ts`, mirrored in the harness): `DEFAULT_COMPACTION_SETTINGS = { enabled: true, reserveTokens: 16384, keepRecentTokens: 20000 }` (lines 106-115). Trigger: `contextTokens > contextWindow - reserveTokens`. Cut-point selection walks newest→oldest accumulating ~`keepRecentTokens`, snapping to valid cut points (never between a tool call and its `toolResult`); if the cut lands mid-turn it generates a **split-turn** two-part summary (`TURN_PREFIX_SUMMARIZATION_PROMPT`). The summary LLM call uses a structured prompt (sections: Goal / Constraints & Preferences / Progress (Done/In Progress/Blocked) / Key Decisions / Next Steps / Critical Context), `maxTokens = min(0.8*reserveTokens, model.maxTokens)`, an "update" variant when a previous summary exists, and `/compact <instructions>` appends "Additional focus: …". `CompactionDetails` tracks cumulative `readFiles`/`modifiedFiles` lists appended as `<read-files>/<modified-files>`. Tool results are clipped to `TOOL_RESULT_MAX_CHARS = 2000` for summarization input. Extensions can intercept via `session_before_compact` (can cancel or supply their own `CompactionResult`).

**Extensibility** — the defining subsystem:
- **Extensions** are TypeScript modules loaded **in-process via jiti** (no build step; `extensions/loader.ts:389-397`), discovered from project `.pi/extensions/`, global `~/.pi/agent/extensions/`, config and `-e` paths. An extension default-exports `(pi: ExtensionAPI) => void`. `ExtensionAPI` (`extensions/types.ts:1165-1399`): `on(event, handler)` (~33 events), `registerTool`, `registerCommand`, `registerShortcut`, `registerFlag`, `registerMessageRenderer`/`registerEntryRenderer` (custom TUI rendering), `registerProvider` (custom LLM providers incl. OAuth), `sendMessage`/`sendUserMessage` (with `deliverAs: steer/followUp` and `triggerTurn`), `appendEntry` (persisted extension state), `exec`, `setModel/setThinkingLevel`, `getActiveTools/setActiveTools`, and a shared `EventBus`. Event catalog spans lifecycle (`session_start/shutdown/before_switch/before_fork/before_compact/compact/before_tree`), loop mirroring (`agent_start/end`, `turn_start/end`, `message_*`, `tool_execution_*`), **interception points** (`input` → transform/handle user input; `tool_call` → block or mutate args; `tool_result` → rewrite results; `context` → mutate the LLM message array; `before_provider_request`/`before_provider_headers`/`after_provider_response`; `user_bash`; `project_trust`), and `model_select`/`thinking_level_select`. `ctx.ui.*` gives dialogs (`select/confirm/input/notify`), widgets/footer/header/title, editor control, autocomplete providers, and `ctx.ui.custom<T>()` for arbitrary TUI components.
- **Skills**: Agent Skills-compatible `SKILL.md` with frontmatter (`name` ≤64 `[a-z0-9-]`, `description` ≤1024 required, `disable-model-invocation`); discovered from `~/.pi/agent/skills/`, `~/.agents/skills/`, project `.pi/skills/` and `.agents/skills/` (trust-gated), packages, and settings (can point at `~/.claude/skills`). Presented to the LLM as an **`<available_skills>` list in the system prompt** (name/description/location); the model then `read`s the SKILL.md — progressive disclosure, no dedicated tool. Skills also become `/skill:name` slash commands.
- **Prompt templates**: `.pi/prompts/*.md` + global, frontmatter `description`/`argument-hint`, invoked as `/name args` with bash-style substitution `$1`, `$@`/`$ARGUMENTS`, `${N:-default}`, `${@:N:L}` (`prompt-templates.ts:69-101`).
- **Themes**: JSON themes in `.pi/themes/`, built-ins `dark`/`light`, live-watched.
- **Pi packages** (`package-manager.ts`): install bundles of extensions/skills/prompts/themes from `npm:@scope/pkg@ver`, `git:host/repo@ref`, or local paths into `~/.pi/agent/npm|git/` (or project `.pi/`); a package declares resources via a `pi` manifest in its package.json or by convention dirs; glob include/exclude filtering per consumer. The `piConfig.configDir` field in coding-agent's own package.json lets forks rebrand `.pi`.
- **Settings**: `~/.pi/agent/settings.json` deep-merged with project `.pi/settings.json` (trust-gated); notable keys with defaults: `theme:"dark"`, `steeringMode/followUpMode:"one-at-a-time"`, `compaction.{enabled:true,reserveTokens:16384,keepRecentTokens:20000}`, `retry.{enabled:true,maxRetries:3,baseDelayMs:2000}`, `defaultProjectTrust:"ask"`, `enableSkillCommands:true`, `packages[]`, `httpProxy`, `images.autoResize:true`.
- **Project trust** (`trust-manager.ts`, `docs/security.md`): loading project `.pi/settings.json`, extensions, skills, prompts, themes, and `SYSTEM.md` requires a trust decision persisted per-directory in `~/.pi/agent/trust.json`; explicitly documented as "an input-loading guard", *not* a sandbox.
- **Auth**: `~/.pi/agent/auth.json` (proper-lockfile-guarded) stores API keys and OAuth credentials; OAuth providers: Anthropic Claude Pro/Max, OpenAI Codex (ChatGPT), GitHub Copilot; env vars are the other path (e.g. `ANTHROPIC_OAUTH_TOKEN` takes precedence over `ANTHROPIC_API_KEY`, `providers/anthropic.ts:14`). `ModelRegistry` merges built-in catalog + user `models.json` custom models/providers and handles token refresh with backend locking (`auth-storage.ts:416-421`).
- **Built-in slash commands** (`core/slash-commands.ts:19-42`): `/settings /model /scoped-models /export /import /share /copy /name /session /changelog /hotkeys /fork /clone /tree /trust /login /logout /new /compact /resume /reload /quit` — everything else comes from templates, skills, or extensions. `!cmd` runs bash into context, `!!cmd` excluded from context (`BashExecutionMessage.excludeFromContext`, `core/messages.ts:29-40`).
- **Self-extensibility story**: every customization doc opens with "pi can create X — ask it"; the system prompt points the model at its own docs/examples; `/reload` (or `ctx.reload()`) hot-reloads extensions/skills/prompts/themes in place; `pi.registerTool()` works at runtime and new tools are immediately callable mid-session (via `addedToolNames` deferred-tool plumbing); extension state survives reload via `appendEntry` + `session_start` replay. The repo's own `.pi/` and the shipped `examples/extensions/` (including a Gondolin micro-VM sandbox and custom-provider examples) are working references.

No `pi-web`/`pi-remote` packages exist here; Slack/chat automation lives in the separate `earendil-works/pi-chat` repo (README.md:35).

## 5. packages/tui (brief)

A dependency-light TUI library (only `marked` + `get-east-asian-width`). Core abstraction: `Component { render(width): string[]; handleInput?; invalidate() }` (`tui.ts:63-88`) — components render to plain strings; the `TUI` class diffs. **Differential rendering** (`doRender`, `tui.ts:~1250+`): full redraw only on first render, terminal width change, height change (except Termux soft-keyboard toggles), or content shrink; otherwise it computes the first/last changed line range against `previousLines`, has a fast **append-only path**, moves the cursor relatively, and repaints only changed lines — all wrapped in **synchronized output** (`CSI ?2026h/l`) for flicker-free updates. Extras: Kitty/iTerm2 inline image protocol (image-aware diff-range expansion and deletion), OSC-11 background-color detection for light/dark theming, bracketed paste, overlay stack (dialogs composite over content pre-diff), hardware-cursor tracking for IME. Components: `Text, TruncatedText, Markdown (custom marked renderer), Editor` (kill-ring, undo stack, autocomplete, word navigation), `Input, SelectList, SettingsList, Loader, Box, Image, Spacer`. Keybinding system with configurable chords (`keybindings.ts`, `DEFAULT_EDITOR_KEYBINDINGS`); native `.node` prebuilds for Windows/macOS modifier-key handling. Tests run against `@xterm/headless` as a reference terminal emulator.

## 6. Design philosophy & notable decisions

- **Minimal harness, extension-first.** README Philosophy (packages/coding-agent/README.md): "Pi is aggressively extensible so it doesn't have to dictate your workflow… This keeps the core minimal." Explicit non-features, each with an escape hatch: **No MCP** ("Build CLI tools with READMEs… or build an extension that adds MCP support"), **No sub-agents** ("Spawn pi instances via tmux, or build your own"), **No permission popups** ("Run in a container, or build your own confirmation flow with extensions"), **No plan mode**, **No built-in to-dos** ("They confuse models. Use a TODO.md"), **No background bash** ("Use tmux. Full observability").
- **No permission system / no sandbox — deliberate** (`docs/security.md`): "A partial in-process sandbox would be easy to misunderstand as a security boundary… Real isolation needs to come from the operating system or a virtualization/container boundary." Instead: project trust as an input-loading guard, plus three documented containerization patterns (Gondolin micro-VM extension keeping auth on host, plain Docker, OpenShell). The `beforeToolCall`/`tool_call` hooks exist precisely so users can build their own permission flows.
- **Small context footprint**: 4 default tools, a ~25-line system prompt, one-line tool snippets, skills as an XML list read on demand, compaction thresholds tuned to reserve headroom rather than maximize retention.
- **The agent can explain and extend itself**: docs and examples ship inside the npm package; the system prompt hard-codes their absolute paths; `/reload` + runtime `registerTool` close the loop so pi can write and load its own extensions within a session.
- **Session portability**: provider-agnostic `AgentMessage` transcript + `transformMessages` normalization means one session can hop across Anthropic/OpenAI/Google/etc. mid-conversation; sessions are plain JSONL, exportable, forkable cross-project, and publicly shared by the author as HF datasets (README.md:75-89).
- **Engineering culture** (AGENTS.md): erasable-syntax-only TS run directly from source, no inline imports, generated model catalog never hand-edited, multi-agent git etiquette (multiple pi sessions share one worktree; `git add -A`/`reset --hard` banned), lockstep releases with local smoke tests via tmux-driven interactive runs, and heavy supply-chain pinning — the repo is visibly built *by* the agent it contains.
